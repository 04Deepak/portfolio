Case study

TumharaJob ATS

A live job portal with a chat feature that didn't quite work, and a deployment story that needed rewriting. I did both.

Role
Full-stack + DevOps / platform
Timeline
May 2026 — ongoing
Stack
Node · Express · React · Socket.IO · MongoDB · Kubernetes · ArgoCD

The problem

TumharaJob connects candidates, employers and institutes, and its real-time chat is how they actually talk to each other. Three bugs were reported against it, all of the worst kind — intermittent, user-visible, and impossible to reproduce reliably:

  • Users flipped to offline whenever they refreshed the page.
  • After a refresh, messages stopped arriving in real time — only a reload showed them.
  • When one participant's socket broke and reconnected, delivery failed entirely.

Three symptoms, three different root causes. None of them were in the chat UI where the bug reports pointed.

Finding the actual causes

The reconnect handler was bound to the wrong object

The client listened for reconnect on the socket instance. In Socket.IO v4 that event fires on the Manager, not the socket — so the handler never ran, and nothing re-subscribed after a reconnection. Moving the listener to the Manager fixed the silent-after-reconnect case.

A dependency array was tearing down every listener

fetchHistory was declared inline and passed into a useEffect dependency array. It was a new function identity on every render, so the effect tore down and re-registered its socket listeners continuously. Stabilising it with the useRef callback pattern stopped the churn.

History was overwriting live messages

The fetch resolved with setMessages(response.data) — a full replace. Any message that arrived over the socket while the fetch was in flight was silently wiped. I switched to appending and de-duplicating on message ID, which makes the two sources safe to interleave.

The pattern: all three bugs looked like "chat is broken" but lived in lifecycle and state management, not in messaging logic. Reproducing each one against two live logins — an employer and a candidate — was what made them findable.

What I built on top

  • A catch-up sync endpoint so a reconnecting client fetches only what it missed, rather than re-pulling an entire conversation.
  • A five-second disconnect grace period, which stopped the false-offline flicker on refresh — a socket dropping is not the same as a user leaving.
  • Dual-emit to both the conversation room and the user's own channel, so delivery no longer depends on a single subscription surviving.
  • A compound MongoDB index on conversation and creation time, so history queries stayed fast as volume grew.

The DevOps half

The application secrets — including payment gateway keys — were sitting hardcoded in the build specification. I moved them out to build-time environment variables, then into a managed secret store, and wrote a GitHub Actions workflow to apply them into the cluster rather than having anyone do it by hand.

From there I took the deployment through a GitOps rebuild: sixteen improvements including autoscaling tuning, PodDisruptionBudgets, rolling update strategy, and restructuring the ArgoCD applications into an App-of-Apps pattern. I also ran a three-repository codebase audit that produced 41 findings, delivered as written reports.

Config that deploys itself

The piece I'm most pleased with: backend configuration — not just secrets — now lives in the secret store and reaches the cluster on its own. A custom resource syncs a config folder into a ConfigMap, and Stakater Reloader watches that ConfigMap and triggers a rolling restart when it changes.

I verified it end to end by flipping a single test key in the secret store and watching the operator sync, Reloader restart the deployment, and a new ReplicaSet come up with the new value — then reverting it. No redeploy, no pipeline run, no one editing YAML.

Production incidents

  • 413 on every upload. The cause wasn't the backend at all — API routes were passing through the frontend's nginx catch-all, which had its own body-size limit. Raising it in the frontend config fixed it.
  • The kubelet kept crashing. A stale fstab entry re-enabled 6 GB of swap on a 2 GB server after every reboot. Disabling swap ended the crash loop.
  • Intermittent CORS failures traced to a misconfigured base URL rather than a CORS policy.

Outcome

Chat works through refreshes and reconnections. Secrets are out of source control and out of build config. Configuration changes reach production without a deploy, and the cluster's bootstrap is captured as code — with the two out-of-band credentials documented as commands to run, never as values in a file.

The frontend was also cut over from a CDN origin to the Kubernetes cluster, with certificates issued automatically through an ACME challenge.
