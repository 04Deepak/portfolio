Case study

LearnHub

A white-label learning platform that any organisation can run as their own — built from a blank page to a production cluster.

Role
Full-stack engineer + platform
Timeline
May 2026 — ongoing · largest project by effort
Stack
TypeScript · Express 5 · MongoDB · Redis · Bull · FFmpeg · Next.js · K3s · ArgoCD

The brief

Build a Udemy-style video learning platform that can be sold white-label: every organisation gets its own branding, its own landing page, its own students — running on one shared system. That means multi-tenancy has to be designed in from the first line, not retrofitted.

I started with the documents rather than the code. A business requirements document, a software requirements spec covering 70+ functional requirements across 16 collection schemas, a functional requirements document spanning 19 modules, and a nine-section architecture document including an infrastructure cost estimate for the client presentation.

Architecture

The backend is layered — config, middleware, models, services, controllers, routes, validators, workers, types — with a deliberate middleware chain that every authenticated request passes through:

  • Request ID assignment, so a request can be traced through logs end to end.
  • Auth, then role guard for the four-role permission model.
  • Org resolver — maps the incoming request to its tenant, cached in Redis for five minutes so tenancy lookup isn't a database hit on every call.
  • Validation via schema, then rate limiting, then a central error handler built on a custom error type and an async wrapper.

Multi-tenancy and access control

Four roles: super admin, organisation admin (which inherits instructor permissions), instructor, and student — with a super-admin bypass in the role guard. Authentication uses short-lived access tokens with rotating refresh tokens, OTP, and per-role device limits: students get one active device, everyone else gets two. Students can log in with either a mobile number or an email address.

Each organisation gets path-based routing, org-scoped student registration, its own uploaded logo, and theme customisation where two brand colours are expanded into a full palette. Public landing pages are generated per organisation.

The video pipeline

This was the hard part, and the reason the project took as long as it did:

  • Chunked upload to S3-compatible object storage, so large lecture files survive imperfect connections.
  • A job queue driving FFmpeg to transcode each upload into HLS at four renditions — 360p through 1080p — off the request path entirely.
  • Signed-URL streaming with a per-organisation watermark that moves around the frame, which makes casual screen-recording piracy meaningfully harder.
  • Free preview lessons on paid courses, so the paywall has a door in it.

The player is deliberately conventional — quality and speed controls, double-tap and arrow-key five-second skip, mobile responsive. Students already know how a video player works; novelty there is a cost, not a feature.

Progress tracking without hammering the database

Watch progress writes through a Redis cache: the client heartbeats every ten seconds, and progress batches to the database every sixty. A lesson counts as complete at 90% watched. The result is accurate resume behaviour without a write amplification problem.

Problems worth remembering

  • Stale unique indexes broke user creation. After a schema change, partial-filter unique indexes on mobile and on the email/organisation pair were left over from the old shape. Dropping and recreating them fixed it — a reminder that indexes are state, not code.
  • A major ODM upgrade removed a type I relied on and changed async pre-hook behaviour; the framework upgrade alongside it started casting route parameters as strings. Both needed real code changes, not just version bumps.

Shipping it

The original plan was a single VPS with a process manager. I moved it to Kubernetes with ArgoCD GitOps, a self-hosted secret store, and self-hosted object storage — which gave a reproducible deployment and kept the infrastructure cost roughly at the estimate I'd put in the architecture document.

Manifests are split across application, infrastructure and ArgoCD directories, with CI and build-deploy workflows and two security audits along the way. Local development uses deliberately non-default database ports so the project can run alongside others on the same machine without a port collision.

Still ongoing. I review pull requests on this codebase — including catching placeholder marketing copy that had been committed as real schema defaults, and verifying the fix landed.
