Case study

NGO Platform & Community App

Two applications, one self-hosted cluster, zero manual deployments — plus the cloud bill guardrails that came from learning the hard way.

Role
DevOps / platform + backend
Timeline
June 2026 — ongoing
Stack
K3s · ArgoCD · Prisma · PostgreSQL · Redis · Turborepo · GHCR · AWS S3

The setup

Two separate products needed to run for the same client: an NGO platform with a conventional backend/frontend split, and a community application built as four backend microservices with its own admin interface. Rather than two environments, both went onto a single self-hosted Kubernetes cluster with namespace separation.

Everything is delivered by ArgoCD pulling from a dedicated GitOps repository, with automated pruning and self-healing enabled. Nothing reaches the cluster because someone ran a command; it reaches the cluster because a commit landed.

The NGO platform

  • Backend and frontend deployed as container images from a registry, with health probes, horizontal pod autoscaling and PodDisruptionBudgets so scaling events and node maintenance don't take the service down.
  • Database migrations and seeding run through Prisma — master category and item reference data, and legal agreement records.
  • Fixed a crash loop, login and CORS failures, and broken object-storage uploads during bring-up.

An AWS account suspension, and what it taught me

The client's original AWS account was suspended, which took document storage down with it. I migrated storage to a new account and reconfigured bucket CORS — and then, because the same failure mode should not be possible twice, set up billing guardrails: budgets and alarms at a deliberately low threshold, with a service control policy that denies further spend at 100% of budget.

A hard stop is better than a surprise. For a non-profit's infrastructure it's the only responsible default.

The community app

Four services — users, chat, forum and notifications — plus a Next.js admin interface. I authored the Kubernetes manifests for all of them, the ArgoCD application that delivers them, and their secret synchronisation resources.

Authentication uses asymmetric JWT signing: the user service holds the private key and signs, and every other service verifies with the public key. No shared secret to distribute, and a compromised forum service can't mint tokens.

The frontends were originally destined for a managed hosting platform, but the client required on-server deployment — so they were containerised and moved onto the cluster alongside everything else.

Shared infrastructure

PostgreSQL runs as a StatefulSet with Redis alongside it in a shared namespace, exposed to each application namespace through alias services. That keeps one database platform to operate rather than one per app, while the applications still address it as though it were local to them.

A self-hosted secret manager is the single source of truth for configuration, synchronised into Kubernetes secrets on a short interval using a machine identity rather than a human's credentials.

When the tool fights you: the secret manager's web interface refused to create a machine identity. Rather than stall, I created the identity, membership and auth records directly in its own database with a properly hashed client secret — then went back and documented the path so it was reproducible.

Debugging notes

  • Registry pulls returned 403. The CI job's default token didn't carry the permissions needed for cross-repository image pulls; switching to a scoped personal access token fixed it.
  • A seed script failed on module resolution. Running it inside a mounted container with the right runtime and TLS library avoided fighting the host environment.
  • A schema field had been renamed in code but not in the database, leaving a partially applied migration. Resolved by aligning the column and marking the migration applied rather than forcing a destructive reset.
  • An organisation policy disabled deploy keys mid-project, so continuous delivery stayed on the side that had write access while the client's side kept CI only.

A "networking" problem that wasn't

A developer's connection to the staging database started failing. I worked outward: checked firewall drop counters to rule out packet filtering, verified the SSH daemon's forwarding configuration, and created a dedicated no-login account for tunnelling. The actual cause was a password authentication failure on the database role — the network was fine the entire time.

Worth the walk. Ruling things out in order is what makes the last answer trustworthy.
