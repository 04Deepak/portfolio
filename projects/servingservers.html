ServingServers

A marketplace where strangers rent your GPU and run their own containers on it. The interesting engineering is all in the word "strangers".

The problem

GPU time is expensive and often idle. A marketplace that matches idle hardware to people who need it is a straightforward idea — right up until you consider what you're actually offering: arbitrary code execution, as a service, on someone else's machine.

Every design decision follows from that. A renter must get a usable environment — a real shell, Jupyter, their own Docker image, GPU access — while the host's machine, the platform, and every other renter stay protected from them.

The isolation model

The core decision was to give the user's container no SSH server at all. Running sshd inside the workload would mean shipping a privileged, network-facing service into an environment I assume is hostile.

Instead, two sidecar containers attach to the job's network and process namespaces: one runs SSH, the other a reverse proxy for browser-based access. SSH logins are pinned to a forced command that enters the user's namespaces and drops privileges before handing over a shell. The renter gets a normal-feeling session; the platform never runs their code with more capability than intended.

A shell script did this originally and was fragile — it broke outright on one distribution because of how mount-namespace lookup behaved. I replaced it with a small static Go binary that performs the namespace entry, capability bounding-set drop, and exec as a single process. Static linking meant it stopped caring what the host distribution was.

Seven phases

  • Image catalogue moved from a hardcoded list into an admin-curated database table, seeded with common ML images.
  • Per-job SSH sidecar image built minimal and purpose-specific.
  • Sidecar lifecycle wired into the agent behind a feature flag, so the new path could be rolled out next to the old one.
  • Per-job egress firewall — a dedicated iptables chain dropping private address ranges and their IPv6 equivalent, with DNS restricted to the gateway. A rented GPU should not be able to reach into the host's private network.
  • Inter-rental cleanup — verified workspace wipe, GPU memory reset, and quarantine for any slot that fails to clean.
  • Multi-image support with browser-based notebook access.
  • Billing and abuse safeguards — a versioned terms gate, auto-suspension on abuse reports, and a per-job egress byte cap with soft and hard limits on a rolling window.

Attacking my own design

Building the isolation is the easy half. I ran two adversarial pentests against it — roughly a thousand lines of security tests across six files, running real attacks over a real SSH session rather than asserting on configuration.

The tests tried to:

  • Attach a debugger to the SSH daemon from inside the workload.
  • Read another process's environment out of /proc to steal secrets.
  • Fill the host's disk from the workspace.
  • Reach the reverse proxy's admin API and reconfigure routing.
  • Exfiltrate data over DNS.
  • Escape the container via a cgroup release-agent.

Those tests produced 17 critical, 25 high, 38 medium and 5 low findings — all of which I fixed, along with a written threat model, vulnerability log, and a repeatable pentest playbook. Hardening that came out of it included one-time single-use terminal tokens with a short TTL, request body limits, content security policy headers, correct handling of a password-hashing length limit, and locking the proxy's admin API down to loopback and gateway traffic only.

Why this project matters to me: it's the one where I had to assume my own users were adversaries, and where writing the exploit was the only honest way to know whether the defence worked.

Debugging highlights

  • Notebooks served a blank page. I'd set the wrong environment variable — one belonging to a different ML platform's convention rather than the notebook server's own. Switching to the correct base-URL argument, and telling the proxy to preserve the path prefix, fixed it.
  • "Network unreachable" on one port turned out to be connection tracking behaving unreliably in a virtualised Docker networking stack. A stateless accept rule for non-SYN traffic worked around it.
  • GPU access was blocked by an over-aggressive capability drop; scoping the device flag properly restored it without giving the capability back.
  • A frontend framework upgrade broke the build over a strict-mode rule about non-deterministic values during render, plus a renamed component prop.

Outcome

Seven phases delivered, every pentest finding closed, a 500-line technical overview written, and a generated client-facing document produced for a delivery meeting. The security work is documented well enough that someone else could re-run the attacks and check my answers — which is the only standard worth holding security documentation to.
